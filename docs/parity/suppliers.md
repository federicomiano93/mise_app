marked **spec** are pinned by a current test (a port runs that test against both files, or re-states it as a

⚠️ **Two parts of this section can do real harm.** (1) **Money**: a card opened without its stored price, or a price
box that re-prices on a format change, silently changes the cost of every recipe and stocktake that uses the
ingredient (items C28, C67, C73; four review rounds of the invoice import each found a price-corruption path, I79).
(2) **Allergens**: the card is where a person declares what an ingredient contains, and the only thing that may ever
write `allergensCheckedAt` is a person ticking «I have checked» (items C98–C109). The pack-list reader and the invoice
import only PROPOSE, or write nothing at all (C105, I16).

S7. **Getters read the session at the moment of use, never captured**: `deleteIngredient`, `mergePacks`, `toggleFavouriteSupplier` are `get` accessors because the session arrives AFTER the module runs (`registry-main.js:105-131`; `registry.js:545-563` reads them each time a card is built). ## The page, the lists, suppliers: Data — read and written

**Collections (all under `locations/{lid}/…` through `pathFor`, which THROWS if no venue is open: `js/location.js`; `firebase-orders.js:61-90`; `record-data.js:14`)**

S18. **Live reads on the page, four listeners, opened at module load after `await sessionReady`**: `suppliers` (whole collection), `ingredients` (whole collection), `ingredient-prices` (whole collection, `includeMetadataChanges`), `config/orders` (one doc) (`registry-main.js:233-272`; `firebase-orders.js:107-119,366-386,453-466`). Unbounded on purpose: "a handful of documents and every one needed to draw the screen". Cost note: every open of the page reads all of the 4. Already in Mise 2 (reuse): `app/src/foodcost/foodcostSource.ts:125,186-196` and `stocktakeSource.ts:80,185-195` read `ingredients` + `ingredient-prices` and lay prices on with `withPrices` (nothing emitted until the ingredients arrive; a refused price read emits them unpriced); `recipesSource.ts:135-139,177,236` reads ingredients (every price key removed) and suppliers quietly (warn, not error). None of the three reads `config/orders`, nor emits the "prices readable" flag.
S19. **Every document gets `bakery: <venue id>` stamped on write** (`withBakery`, `record-data.js:45`; `firebase-orders.js:96-98`); the rules require `request.resource.data.bakery == lid` (`stampedFor`). Writes are `setDoc(..., {merge:true})`, so rules see the FULL MERGED document: nothing may be required and every field production ever carried must stay whitelisted.
S20. **`suppliers/{id}` whitelist** (rules `:554-607`): keys `bakery, name, shortName, category, phone, email, deliveryDays, orderDays, active, notifyHoursBefore, vatNumber`. Sizes: `name ≤200`, `shortName ≤60`, `category ≤200`, `phone ≤40`, `email ≤320`, `vatNumber ≤30`, `deliveryDays` and `orderDays` lists `≤7`, `active` bool, `notifyHoursBefore` null or number. Nothing required. ⚠️ `notifyHoursBefore` is retired but stays whitelisted for good (production carries it; removing it makes old suppliers permanently unwritable).
S21. **`ingredients/{id}` whitelist** (rules `:720-…`): keys `bakery, name, shortName, supplierId, brand, weight, category, unit, active, kind, priceUnit, pricePerUnit, packPrice, packSize, unitWeightKg, priceUpdatedAt, allergens, mayContain, allergensCheckedAt, nutrition, packIngredients, packUnit, packCount, supplierCode, supplierCodes, invoiceName`. Sizes: `name ≤200`, `invoiceName ≤1000`, `shortName ≤60`, `supplierId ≤200`, `brand ≤200`, `weight ≤100`, `category ≤200`, `unit ≤100`, `packUnit ≤40`, `packCount` null or int 1..10000, `supplierCode ≤60`, `supplierCodes` list ≤20, `allergens`/`mayContain` lists ≤40, `nutrition` map with only `kj,kcal,fat,saturates,carbs,sugars,protein,salt`, `packIngredients` null or ≤4000 chars, `allergensCheckedAt` null or string ≤64, `kind` absent/null/`'ingredient'`/`'packaging'`. ⚠️ Stay for good: `packUnit`, `supplierCodes` (and `supplierCode`), plus the six OLD price keys, which are accepted ONLY as `null`.
S22. **⚠️ The old price keys on `ingredients` are written `null` on EVERY ingredient save** so they drain out: `splitPriceFields` (`js/price-model.js:848`), and also by the category bulk write (`category-batches.js:30-35`: `categoryPatch` sets `category` plus every `INGREDIENT_DRAINED_FIELDS` key to null). A write of the category alone to an old ingredient still carrying numeric legacy keys is refused on the merged doc and takes the whole batch with it. **spec** `category-batches`, `price-fields-whitelist`. Already in Mise 2: `INGREDIENT_DRAINED_FIELDS`/`PRICE_FIELDS` in `shared/src/price-model.ts:144-160`; `splitPriceFields`, `pricePatch`, `priceRecord`, `priceChanged`, `formatPricePerUnit` are NOT ported.
S23. **`ingredient-prices/{ingredientId}`** (doc id = the ingredient's id; a parallel collection, not a subcollection, for read cost; rules `:643-…`): keys `bakery, priceUnit, pricePerUnit, packPrice, packSize, unitWeightKg, priceUpdatedAt, vatRate, casePrice, caseCount, caseItemSize, caseItemUnit, priceBasis`. `priceUnit` ∈ `kg,l,pcs`; `pricePerUnit`, `unitWeightKg`, `casePrice`, `caseCount`, `caseItemSize` null or >0; `caseItemUnit` ∈ `pcs,kg,g,l,ml,pack`; `vatRate` null or ∈ 0,4,5,10,20,22 (null = "not stated", never read as 0, 0 is a real answer); `priceBasis` null or ∈ `pack,case,rate`; `priceUpdatedAt` ≤64. Read: `cardAccess(foodcost)≠none`; create/update/delete: `canManage(foodcost)`. ⚠️ `vatRate`, the case keys and `priceBasis` live ONLY here; one refused key fails every ingredient save. ⚠️ `priceBasis` stays for good. **spec** `price-fields-whitelist`.
S24. **The prices listener tells the screen whether it really answered** (second argument `readable`): `!fromCache || !empty`, and `false` on error (`firebase-orders.js:366-386`). `includeMetadataChanges` is needed or an empty collection never becomes "readable" (6 Oct 2026 bug: invoice import of an empty-price venue said "still loading" for ever). A cached empty answer proves nothing because the refusal may not have arrived. Port requirement: keep the `readable` flag with these semantics; the ingredient list must show NO price (not an error) for a person refused the collection.
S25. **`ingredients/{id}/prices/{autoId}` = append-only price history** (rules `:922-…`): create-only (`update, delete: if false`), `canManage(foodcost)`; keys `bakery, recordedAt, priceUnit, pricePerUnit, packPrice, packSize, unitWeightKg, supplierId, source, invoiceId, invoiceDate, invoiceQty, packLabel, packCode`; `source` is `manual` (no invoice keys) or `invoice` (id `inv-<invoiceId>-<n>`, date `YYYY-MM-DD`). ⚠️ `packLabel ≤120` and `packCode ≤60` stay for good. `priceBasis` is NOT in it. Read = `cardAccess(foodcost)≠none`. A subcollection inherits nothing from its parent's rules. The history is read ON DEMAND newest first, `orderBy('recordedAt','desc') limit(20)` (`getPriceHistory`, `firebase-orders.js:393-402`); ⚠️ never `orderBy(documentId(),'desc')`.
S26. **`config/orders` fields this page reads/writes**: `ingredientCategories` (list ≤100), `weekStartsOn` (string ≤16, default `Sunday`; read only to hand to the price-changes screen, `work-week.js weekStartOf`), `favouriteSuppliers` (list ≤300), plus `supplierOrder` (list ≤300; written by Orders settings, NOT touched here). ⚠️ `supplierOrder` and `favouriteSuppliers` stay in the `config/{doc}` whitelist for good: removing either would refuse EVERY `config/orders` save (stock switch, send routes, week start). The whole `config/{doc}` key list is shared with the Calculator's `config/calculator`. Doc `config/orders` is never deleted (rule).
S27. **`ingredientCategories` semantics**: absent/not-a-list = "never saved one, or not loaded yet" → offer the defaults; **an empty list is an answer** (the venue deleted every category) (`registry-main.js:257`; `record-choices.js`). Defaults: Italian `Panetteria, Pasticceria, Vendita`; English `Bakery, Pastry, Retail` — venue OUTPUT language (country), plain constants, never `t()` keys (`record-choices.js`). **spec** `record-choices`. The menu always also offers every category in use and the item's own current value (see item S106).
S28. **«Missing» config only counts as loaded when the server said so**: `state.loaded.config = true` only if `doc !== null || !fromCache` (`registry-main.js:260-263`). A cold start offline reports a missing doc from an empty cache; treating that as loaded would let a category delete overwrite the real list with defaults-minus-one. **spec** `category-settings-guards`.
S29. **`favouriteSuppliers`** = array of supplier ids, venue-wide, normalised on read: unique, non-empty strings, order kept, capped at 300; anything not an array = none (`favourite-suppliers.js:6-18`). Written ONLY with `arrayUnion`/`arrayRemove` through `saveDoc('config','orders', …)` (so two managers starring at once never overwrite each other; never a read-modify-write of the whole list) (`firebase-orders.js:239-243`). An id matching no supplier (deleted) is ignored when drawing and never cleaned up. **spec** `favourite-suppliers`.
S30. **The "no supplier" pseudo-supplier**: id string `'no-supplier'` (`js/records.js`), STORED on ingredients as `supplierId`; NEVER written to `suppliers`; an ingredient whose `supplierId` points at nothing (deleted or never set) is "No supplier" in the UI (`no-supplier.js:36`, Orders' lens). On this page it is not a list row; see Finding S-B. Already in Mise 2: no.
S31. **Supplier save** = ONE `setDoc(ref, withBakery(payload), {merge:true})`; the id is minted before the write (`doc(collection)` auto-id) and returned, so "+ New supplier" inside an ingredient card can select it immediately (`record-data.js:137`). Merge keeps fields a newer screen wrote that this form does not know. **spec** `record-cards-shared` ("a new supplier gets its id BEFORE the write").
S32. **Ingredient save = one atomic batch** (`record-data.js`): the ingredient doc (price keys nulled, `merge:true`), and ONLY IF `writePrice`: `ingredient-prices/{sameId}` (`merge:true`) and, ONLY IF a price record is passed, a new auto-id doc in `ingredients/{id}/prices`. The id is minted client-side so a brand-new ingredient, its price and its first history line land together or not at all. `priceRecord` is `null` when the price did not move (no non-event lines in the history). `writePrice` is passed in, never decided in the data layer: a batch is all-or-nothing, so a price write for someone the rules refuse would fail a rename with a permission error.
S33. **After an ingredient save the page fires `mise:action` events** `ingredient-saved` (and `price-saved` if a price record was written) for usage counting; for a supplier `supplier-saved` (`registry-main.js:93-94`; `registry.js:487`). Already in Mise 2: the `m2:` usage mechanism is referenced by the catalogue list; names to keep: `ingredient-saved`, `price-saved`, `supplier-saved`.
S34. **Changing the order unit via the card freezes the open order-draft line** (`meta.unitChangedFrom` → `freezeUnitInDraft`, `draft.js:297-308`): a draft line with a quantity and no unit of its own gets the OLD unit written onto it, so "8 buste" stays 8 buste. NOT part of the save; if it fails the ingredient is already saved and only the log says so (`registry-main.js:95-98`).
S35. **Ingredient delete = one batch** deleting `ingredients/{id}` and, only where `mayWritePrices()`, `ingredient-prices/{id}` (`record-data.js:60`; `ingredient-edit-model.js:38-43` `deletePlan`). The price HISTORY subcollection is NOT deleted (rules forbid; it stays orphaned and unreachable). Past orders keep the ingredient's frozen name (`orders-history.names`). After the delete the entry is cleared from the shared draft (`drafts/current`, field `entries.<id>`, via `deleteField`), fire-and-forget, failure only logged (`draft.js:268-282`; `ingredient-edit-model.js:48-50`). **spec** `ingredient-delete`.
S36. **Supplier delete = one `deleteDoc`** (`removeDoc`, `firebase-orders.js:328-331`). It does NOT touch ingredients, favourites, the draft, `supplierOrder` or history (see item S87). Rule: `canManage(orders)`.
S37. **Supplier/ingredient deactivate = merge `{active:false|true}`** (`registry-main.js:102`). `active` absent = active (`!== false` everywhere).
S38. **Category delete = batched write**: `setCategoryOnMany(ids, 'Other', {config/orders, {ingredientCategories: shortenedList}})` (`registry-main.js:133-134`; `firebase-orders.js:311-326`). Batches of at most 6 ingredient writes (the config write counts as one and rides in the FIRST batch), because Firestore allows 20 document-access calls per batched write and the rules make ~2 `get()` per ingredient write (the emulator does NOT enforce it); `batch.update()` not `set` so an ingredient deleted meanwhile does not come back nameless (the batch then fails and is reported). Each ingredient is written `category:'Other'` + legacy keys null + `bakery`. `'Other'` is the stored "no category" word (reads back as blank, `record-choices.js:72`). **spec** `category-batches`.
S39. **Local copies / browser storage on this page: none of its own.** No `localStorage`/`sessionStorage` key is read or written by `suppliers.html`, `registry*.js`, the two record forms, `record-*.js`, search box or tablet layout (grepped). Only app-wide things load alongside: `kiosk.js` (device kiosk keys), the service worker, Firestore's offline cache. The search text and the selected tab live in memory only and are lost on reload. The only URL state: `#packaging` selects the packaging tab (`registry.js:137`).
S40. **Module-level memory in `registry-settings.js`** survives the Settings screen being rebuilt: `categorySavedUntil` (a "Saved" chip for 2 s) and `categoryFocusAfter` (where focus goes after a category row is deleted), because every Firestore snapshot rebuilds the open Settings screen (`registry-settings.js:34-43`).
S41. **Offline**: Firestore's offline cache is the only offline story (writes are queued by the SDK; the supplier-star write is deliberately NOT awaited, `registry.js:444-446`). The page never blocks a screen on a write. Already in Mise 2: single backend entry per `docs/architecture.md`.

## The ingredient card: Data — read and written by the card

C13. **Three places, one id.** `locations/{lid}/ingredients/{id}` (product data); `locations/{lid}/ingredient-prices/{id}` (the money, SAME id, a parallel collection not a subcollection: one read feeds Food cost, P14, `rules:634-637`); `locations/{lid}/ingredients/{id}/prices/{autoId}` (append-only price history). Every document carries `bakery: <lid>` (`RD`; rules `stampedFor`). `currentLocationId()` throws if no venue is open.
C14. **What the card writes on `ingredients/{id}`** (merge): `name, shortName, supplierId, brand, weight, category, active, kind`, then only-when-touched `unit, packUnit, packCount`, and for non-packaging `allergens, mayContain, allergensCheckedAt, nutrition, packIngredients` (`form:2224-2240`).
C15. **Never written by the card but kept alive by the merge write:** `invoiceName` (read-only block, `form:1619`), `supplierCode`, `supplierCodes[]` (≤20, invoice import). ⚠️ The card has NO field for supplier codes. A rewrite that replaced the document instead of merging would erase them. **spec** `ingredient-name` («saving never sends invoiceName»)
C16. ⚠️ **Six old price keys are written `null` on the ingredient on EVERY save, for every role:** `priceUnit, pricePerUnit, packPrice, packSize, unitWeightKg, priceUpdatedAt` (`PM:146-148` `INGREDIENT_DRAINED_FIELDS`, applied by `splitPriceFields` `PM:848-861`). The rules accept only `null` there (`rules:813-824`). `vatRate`, the four `case…` keys and `priceBasis` must NEVER be sent on the ingredient: the whitelist lacks them and ONE refused key fails every ingredient save for every role. **spec** `price-fields-whitelist`, `price-model`
C17. **What goes on `ingredient-prices/{id}`** (merge, one document): `priceUnit, pricePerUnit, unitWeightKg, priceUpdatedAt, vatRate, casePrice, caseCount, caseItemSize, caseItemUnit, priceBasis`, plus `packPrice:null, packSize:null` (retired, cleared on every manager save). Closed whitelist, each key optional and validated when present (`rules:650-713`). **spec** `price-fields-whitelist`
C18. **Price-document value rules.** `pricePerUnit`, `unitWeightKg`, `casePrice`, `caseCount`, `caseItemSize` are numbers > 0 or null. `priceUnit` ∈ {kg,l,pcs}. `caseItemUnit` ∈ {pcs,kg,g,l,ml,pack}. `vatRate` ∈ {0,4,5,10,20,22} or null. `priceBasis` ∈ {pack,case,rate} or null. `priceUpdatedAt` is a string ≤64.
C19. **Ingredient-document limits.** `name` ≤200, `shortName` ≤60, `supplierId` ≤200, `brand` ≤200, `weight` ≤100, `category` ≤200, `unit` ≤100, `packUnit` ≤40, `packCount` an int 1–10000 or null, `allergens`/`mayContain` lists ≤40, `allergensCheckedAt` null or a string ≤64, `packIngredients` ≤4000, `nutrition` a map with keys only in {kj,kcal,fat,saturates,carbs,sugars,protein,salt}, `kind` ∈ {ingredient,packaging} or null (`rules:723-883`). The key list is CLOSED. ⚠️ A key outside it refuses the WHOLE document.
C20. ⚠️ **Fields that must stay in the whitelists forever** (production carries them): `ingredients.supplierCode(s)`, `.packUnit`, `.packCount`, `.invoiceName`, the six drained price keys; `ingredient-prices.priceBasis`, `packPrice`, `packSize`; history `packLabel`, `packCode`, `packPrice`, `packSize` (`rules:631-642`, `:934-964`; data-model.md lines 49-73).
C21. **The save is ONE atomic batch** (`saveIngredientWithPrice`, `RD:88`): `set(ingredient, merge)`; if `writePrice`, also `set(ingredient-prices/{id}, merge)` and, if a record exists, `set(prices/{auto})` (history). All or nothing. A new ingredient's id is minted client-side (`doc(collection)`) so the item, its price and its first history entry land together; returns the id.
C22. ⚠️ **`writePrice=false` for anybody who may not write prices is not an optimisation.** Including a refused `ingredient-prices` write would make the DB fail the whole batch, so an ordinary rename would fail with a permission error (`RD`). An employee's payload carries no price keys at all (`patch = {}`), and a manager's carries every price key (value or `null`) so that emptying a box really clears the price over a merge (`form:2201-2210`).
C23. **A history entry is written only when the price is COMPLETE and the MONEY changed:** `record = mayPrice && patch.pricePerUnit !== null && priceChanged(item, patch)` (`form:2249`). Its fields are `recordedAt` (ISO now), `priceUnit`, `pricePerUnit`, `unitWeightKg`, `supplierId` (the saved payload's, '' if none), `source:'manual'`, plus `bakery` (`PM:817-826`). NOT recorded: VAT, case, count, basis (named fields on purpose). ⚠️ **And the price's date (`priceUpdatedAt`) moves by the same rule** (F4, fixed in the current app 20 Oct 2026, `keepPriceDate`, branch `fix/price-date-only-with-money`): when `priceChanged` is false the stored date is kept, so a rename never re-dates an invoice price. Port it with the card save. **spec** `price-model`, `case-price`, `price-basis`, `ingredient-card-save`
C24. **`priceChanged` compares MONEY, not shape.** Per-kilo cost and per-piece cost, each when both sides have it, within `max(1e-6, 0.01%)`. A piece weight appearing or going is a change. With nothing to compare it falls back to `priceUnit/pricePerUnit/unitWeightKg` (`PM:779-800`). No entry for a rename, a Cartone→Singola, a basis-only tap or a retyped identical price. **spec** `price-model`, `price-basis`, `price-basis-card`, `ingredient-card-save`
C25. **History read** (`getPriceHistory`, `js/orders/firebase-orders.js:393-402`): subcollection `prices`, `orderBy('recordedAt','desc')`, `limit(20)`. ON DEMAND only, a «Mostrali» button, never watched (P14). ⚠️ Never order by document id (refused by Firestore). A new item has no history block. A failure re-enables the button and reports `load`.
C26. **History row shows** `formatPricePerUnit(entry)` («£7.20 / kg» or the localized «each»), a «from invoice» tag when `source==='invoice'`, the short date, and the invoice's own pack label on its own line when present (`form:998-1011`). Empty → «no price recorded yet».
C27. **Reopening an existing item needs its price.** The item is the ingredient MERGED with its `ingredient-prices` doc (`withPrices` / `itemWithPrice`, `js/ingredient-edit-model.js:16-19`). `withPrices` blanks every price key found on the ingredient itself and uses only the price document (`PM:878-887`, security audit 23 Sep 2026). **spec** `price-model`, `orders-edit-ingredient`
C28. ⚠️ **A card opened without the stored price is a trap:** the boxes are empty and an untouched Save writes «no price» over the stored one. So for a price writer, while the live price snapshot has not answered, the price doc is read first (`needsPriceRead`, `ingredient-edit-model.js:24`; `readIngredientPrice` `RD:110`). The read THROWS on failure and the caller says «could not be opened» and opens NOTHING (`registry.js:519-532`). A second tap during the read is ignored. **spec** `orders-edit-ingredient`
C29. **The card opens from the list as it is NOW, not from the row's own object** (6th review, 2 Oct 2026, `registry.js:515`).
C30. **Save is NOT local-first.** The card awaits `batch.commit()` (`form:2274`, `RD`); Save stays disabled while it runs; failure → `reportFailure('save', name, err)` and the card stays open, Save re-enabled (`form:2277-2280`). I did not verify what a Firestore web batch does offline here; the Firestore SDK resolves `commit()` only on server acknowledgement. See T3.
C31. **Usage events.** After a save the page dispatches `mise:action` `ingredient-saved`, and `price-saved` when a history record was written (`registry-main.js:92-94`; `ingredient-create.js:192-193`).
C32. **Delete = one batch** `deletePlan({id, mayPrice})` = `[ingredients/{id}]` + `[ingredient-prices/{id}]` only if the person may write prices (`ingredient-edit-model.js:38-43`; `RD:122`). The price-history subcollection is NEVER deleted (the rules forbid it: append-only) and stays behind unreachable. **spec** `ingredient-delete`
C33. **Delete also clears the order draft:** `dropDeletedIngredientFromDraft(id)` → `clearFields(drafts, entries.<id>)` using `deleteField()`, not awaited (card closes at once); failure is only logged (`registry-main.js:113-116`; `js/orders/draft.js:268-282`). `draftEntryPath(id) = 'entries.<id>'` (`ingredient-edit-model.js:48`). **spec** `ingredient-delete`
C34. **A new supplier made from the card is its own write** (`saveSupplierRecord`, `setDoc` merge, id minted first, `RD:137`) that commits before the ingredient is saved. The card keeps its typing underneath.
C35. **Unit change freezes the open order line.** When the format rewrites `unit`, the card passes `{unitChangedFrom}` to the caller; the caller freezes the open draft line in the old unit (`freezeUnitInDraft`, `draft.js:297-308`; Orders `registry-main.js:95-98`; `ingredient-create.js:293`). Failure is only logged: the ingredient is already saved. **spec** `draft-freeze-unit`, `ingredient-card-save`

## Findings — things found while reading, not decided

### Findings — The page, the lists, suppliers

S-A. **First paint shows the empty state before any data arrives.** `buildRegistry` calls `paintList()` at construction with empty getters, so «No ingredients yet…» is drawn until the first snapshot (`registry.js:983`; `registry-main.js:30-46` tracks `loaded.*` but never tells the screen). Probably hidden by the auth-gate cover and the fast cache, but not by any rule. Not verified by driving.
S-B. **Ingredients with a deleted supplier are almost invisible on the Suppliers tab.** Deleting a supplier leaves its ingredients with a dangling `supplierId`; `countBySupplier` counts them under the dead id (shown nowhere) and the pseudo-supplier «No supplier» has no row on this page (it exists only in Orders). They are reachable only through the Ingredients tab (labelled «No supplier»). The delete confirmation does not warn about them.
S-C. **Deactivating a supplier does not hide its ingredients on this page** (Orders hides them); they stay listed under Ingredients, dimmed only if the ingredient itself is inactive. Deliberate or not is unclear.
S-D. **No UI to deactivate or reactivate an ingredient.** `setIngredientActive` is wired in `registry-main.js:103` and documented in `registry.js:72`, but nothing calls it, and the card preserves `active` (`ingredient-record-form.js:2143,2234`). Ingredients with `active:false` (legacy) display dimmed with no way to change that here. Dead action.
S-E. **Supplier category is free text, the ingredient's is a menu.** A supplier's category is not validated, not in `config/orders.ingredientCategories`, and is only shown in the row meta.
S-F. **«Phone (WhatsApp, digits only)» is not enforced**: input is `type=tel`, trimmed only; a `+44 7700 900123` is stored as typed. The message to the supplier uses it (`order-text.js` / send routes); whether the sender normalises it was not checked.
S-G. **`#packaging` has no linker today.** The code comment says Food cost's packaging chooser sends people there, but grep of `js/` and `app/src` finds no `suppliers.html#packaging` link (Food cost shows `fc.noPackagingYet`). The route feature is used by nobody I could find.
S-H. **Sorting uses the device's default `localeCompare`**, not the venue's language, and the supplier search lower-cases without folding accents (Orders folds accents): «Cerca "cafe"» will not find «Caffè» on this page but will in Orders.
S-I. **`.claude/skills/firestore-rules/data-model.md` omits `suppliers.vatNumber`** (line 55 lists the fields without it); the rules (whitelist + `≤30`) and `supplier-record-form.js` carry it.
S-J. **Settings categories list = stored list + categories in use**, so a delete from Settings of a category that was only "in use" writes the whole displayed list (`rest`) back to `config/orders`, quietly turning "defaults + in use" into a stored list (`registry-main.js:61-64`, `registry-settings.js:231-240`). Probably harmless; worth knowing when porting `categoryChoices`.
